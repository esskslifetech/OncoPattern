# Contributing to OncoPattern

OncoPattern is written in **`.tech`** and runs on the [TECH](https://github.com/esskslifetech/TECH)
toolchain. Contributions of `.tech` code, detectors, simulation models, report
sections, fixtures and documentation are welcome. So are defect reports: the
toolchain is young and its failure modes are quiet, so a reproduction is worth
more than a description.

## Before you start

Read the README first — it is the contract this repository is held to. It
carries the build commands, the measured status of the certificates, and a
section called *Notes on the toolchain* that lists the behaviours which will
otherwise cost you an afternoon: `print()` produces no output on the bootstrap
VM, `str<utf8>` does not concatenate with `+`, sized buffers must be global, a
nested `WHILE` inside a `MATCH` `CASE` silently compiles to a 0-byte object.
Code that ignores those notes does not fail — it quietly does the wrong thing.

## Set up

The build needs a TECH checkout. It does not have to be in any particular
place: `tools/ocbuild` looks at `$TECH_ROOT`, then at `../../TECH`, `../TECH`
and `./TECH`.

```bash
git clone https://github.com/esskslifetech/OncoPattern
git clone https://github.com/esskslifetech/TECH        # sibling checkout
cd OncoPattern
tools/runtests                                         # 9 certificates
tools/ocbuild run config/boot.tech oncopattern         # full pipeline
```

Linux or WSL is the supported environment; macOS works with a POSIX shell.
Python 3 (standard library only) is needed for the retrieval and fixture tools.

## The loop

1. Make the change in `oncopattern/`, never in a staged copy under TECH.
2. Add or extend a certificate in `oncopattern/test/` for behaviour you add.
   A new detector asserts the ground truth planted by `tools/gen_datasets.py`;
   a new model asserts something independent of its own implementation
   (conservation, convergence order, an analytic limit).
3. Run `tools/runtests`. **All certificates must pass.** A change that moves an
   assertion count is fine; a change that leaves a failure is not.
4. If a figure quoted in `README.md` changed, update the document in the same
   commit. Numbers in the docs are measurements, not aspirations.

## What to commit, what not to

Tracked: `.tech` sources, the certificates, the input fixtures in `datasets/`
(including the real EPO and Europe PMC pulls — they are small and they are what
makes a run reproducible), the tools, and the documents.

Not tracked: anything the platform produces. `results/`, `dist/`, bytecode,
framebuffers, journals and images are all regenerated by the two commands
above. `.gitignore` already excludes them; please do not force-add them.

Never edit `datasets/*.json` by hand. Regenerate with `tools/gen_datasets.py`
(synthetic, byte-identical) or re-pull with `tools/fetch_patents.py` /
`tools/fetch_papers.py` (live endpoints, counts drift as the databases grow).
The unmodified API responses in `datasets/*_provenance.json` are provenance and
are never rewritten.

## Style

- Follow the surrounding file. `*.tech` uses four-space indentation, an ASCII
  header banner naming the module, `META @module(...)` metadata, and comments
  that explain *why* a construction is shaped the way it is.
- Match on facts, not vibes: every threshold in the platform resolves to a
  published reference or to a stated simulation default with units. New
  constants need the same treatment, and the evidence base is printed in
  section 11 of the report.
- Do not introduce another language into the product. The Python under `tools/`
  is fixture generation, retrieval and preview conversion — it is not part of
  the platform and never runs during a pipeline execution.
- LF line endings, UTF-8, no trailing whitespace. `.editorconfig` and
  `.gitattributes` enforce this for you.

## Commits and pull requests

Write the commit subject as a statement of what changed and what it means, in
the imperative, and put the measurements in the body — a reviewer should be
able to tell from `git log` whether a change moved a number:

```
<module>: <what changed, stated as a result>

<Why the previous behaviour was wrong, or why the new behaviour is better, in
one short paragraph. Quote the before and after — an assertion count, a
conservation residual, a convergence error, a byte size — and name the
certificate that covers it.>
```

In a pull request, say what you changed, what you ran, and what the output was.
Paste the `tools/runtests` summary line. If you fixed a defect, describe the
failure mode, because the next person will hit it.

## Reporting a defect

Open an issue with `tools/runtests` output, the module and function names
involved, and — if the toolchain is implicated — the smallest `.tech` program
that reproduces it. The `scratch/` directory holds the language-probe programs
used to pin down toolchain semantics; a new probe is a legitimate thing to
attach to an issue.
